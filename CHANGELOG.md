# Changelog

All notable changes to the AURIORA Firmware Style Guide are documented in this file. Released versions are tagged in version control.

## 0.6.0 - 2026-09-18

- Stored object retrieval firmware rules (§14.3, extended), following AES 0.9.0 `AES-MCI-008` ([EDR-010](https://github.com/auriora-org/auriora-engineering-standard/blob/main/docs/edr/EDR-010-hub-host-facing-interface-and-stored-object-retrieval.md)): a completed recording, log or committed object is immutable — closed, digested, never appended to, compacted or rewritten in place, with deletion a separately declared operation refused during the producing run; reads are stateless (object, offset, length → the same plus data) with no handles, sequences or host-dependent timers, a declared maximum chunk length, longer requests refused and nothing sent unrequested; a vanished or changed object is refused with the defined error, never substituted; recording metadata (run and segment, deployment and Session identity with hash, local-time and sample-index range, format identifier and version, firmware version, completion state) is written as the object is opened, checkpointed and closed, the inventory is readable before any object and every recording belongs to exactly one segment; an in-progress recording, where offered, exposes only a committed stable prefix; retrieval runs below acquisition, AEL and control in priority, bounded to one chunk per request, verified not to move the sample clock, AEL latency or control response, and refused in `ARMED`/`RUNNING` where that cannot be guaranteed. §14.3's introduction now names stored object retrieval and points to §14.4 for autonomous operation.
- Module Hub host-facing interface and MCI forwarding (new §14.5), following AES 0.9.0 `AES-HUB-003`: the host-facing interface as a transport adapter of the direct local MCI binding with the Hub an addressable endpoint and each Module Port a forwarding path; forward without parsing, caching, reordering, merging or answering for a Module; buffer only responses to outstanding requests, never prefetch or accept unsolicited data; interleave at chunk granularity so a control request to any port is transmitted within one bulk chunk; per-port independence with independent state, timeout and buffers; the AEL router untouched and its timing acceptance-tested under maximum bulk load; USB isolated in the adapter with class and descriptors left to the binding and product; disconnect tests on both the host and the Module side.

## 0.5.0 - 2026-09-17

- Autonomous operation and recovery firmware rules (new §14.4), following AES 0.8.0 `AES-MCI-006`/`AES-MCI-007` ([EDR-009](https://github.com/auriora-org/auriora-engineering-standard/blob/main/docs/edr/EDR-009-autonomous-module-operation-and-recovery.md)): every reset path boots to `IDLE` with safe outputs and a logged reset cause, and only then runs the recovery procedure — validate the persistent deployment state, re-run the same prerequisite and arming checks as `arm`, and transition through the ordinary state machine with `RECOVERY` as the reason, or stay `IDLE` with `RECOVERY_REFUSED` and the reason recorded; persistent deployment state as a versioned, integrity-checked record written atomically (two slots or journaled switch), updated at every transition and boundary and checkpointed at a documented cadence with local time and sample index; a persisted consecutive-recovery counter incremented before the attempt and bounded; a new run segment (or run) per recovery with a recorded boundary and a sample index that never continues across it; host loss as a defined state-machine input (supervision interval or transport-reported), with no link event reaching Session logic under *continue* and the ordinary abort path under *stop*; storage exhaustion as a policy branch — *stop* preserves and completes, *overwrite oldest* records the overwritten extent, and overwrite is never a fallback; fault recovery as a documented table of recoverable / degraded / fatal classes with a retry bound per row and every attempt logged; completion persisted before it is reported and never cleared without a host reading it; readback of policy, recovery count, run/segment identity, reset cause, completion/stop/refusal reason and storage state from persistent state and log; and reset-centred tests — power cycles in every state, corrupt state, missing Unit, recurring fault, both storage and both host-loss behaviors, boundary readback. §14.2's host-loss bullet now names the deployment policy and points to §14.4 as the only path back into execution after a reset.
- AURIORA Event Link (AEL) firmware rules (§14.2), replacing the Module Synchronization Interface section after AES 0.8.0 superseded SYNC with AEL (`AES-AEL-001` to `AES-AEL-005`, `docs/interfaces/ael.md`, EDR-008). Module firmware: receive the four 8N1 characters (1 Mbit/s baseline) through a serial peripheral with DMA and capture the reference instant — the first start-bit edge after the idle gap — by any hardware mechanism, converting to the sample clock where one exists; treat the characters between two qualifying idle gaps as the candidate frame and act only when exactly four arrived without framing error, the fully parameterized CRC-16 matches and the identifier is non-zero, counting and logging everything else without action, with the resulting action-latency floor (frame + gap) stated; hold receive bindings as a validated, readable `event_id → (action, enabled-state mask)` table and source bindings as `internal event → event_id`; run the bounded lookup at ISR/DMA level where its worst case is fixed and schedule the action from the captured reference instant; make every state × event pair explicit, with nothing enabled before `ARMED` and `RUNNING` no longer ignoring events globally — acceptance is per binding, and restart/stop/queue/advance/phase-change exist only as explicitly bound actions; emit AEL OUT from the real internal occurrence through a hardware-timed output, never on command receipt, never `0x0000`, never during power, reset or firmware start; no information in frame timing or repetition, no acknowledgment, no retransmission; log received (acted/ignored + reason), transmitted and invalid frames with timestamp, sample index, state, run identifier and local counters; treat host loss as a scenario governed by the Module's declared capability, with reconnection changing nothing and a reset returning to `IDLE`; host-test every state × identifier including unknown, unbound, disabled, `0x0000` and corrupt frames, and measure latency and jitter under load. Router firmware (new): the event path as a bounded real-time subsystem that management traffic cannot delay, proven by measurement; one hardware receiver and transmitter per port with hardware timestamping; store-and-forward after validation with `(ingress port, event_id)` lookup and fan-out launched from one hardware event; a route table of numbers only, with no mechanism to load experiment logic; stage → validate → commit by atomic switch between frames, refused while a dependent deployment is armed or running, never reinstated from non-volatile memory after reset; fixed-capacity deterministic queues with a documented ordering and overflow rule and every drop counted; full per-port and global observability; and load, corruption, unrouted, refused-commit and power-cycle tests. §14.1 and §14.3 updated to refer to AEL; the capability-table rule in §14.3 now names the AEL properties a host plans against, and configuration readback names the AEL bindings with their per-state enables.

## 0.4.0 - 2026-09-12

- Module Control Interface (MCI) firmware rules (§14.3): implement the operations once behind an internal interface and let transport adapters do framing only, so no handler branches on which transport a request arrived over; answer identity before any configuration, from immutable storage, independent of transport and cable; keep the declared capability set in one place and generate dispatch checks from it, returning a defined "unsupported" error rather than silent success; model `IDLE → CONFIGURED → ARMED → RUNNING → COMPLETE` as an explicit state machine that reports *why* a transition was refused; make entering `ARMED` mean every precondition was actually checked, and report state rather than acknowledgment; never provide a control operation documented as the way to start several Modules together — the deterministic instant belongs to SYNC (§14.2); stage, verify against a whole-object integrity value, then commit, leaving a previously committed object untouched on failure; expose the stored inventory with content identity so a host can skip unnecessary transfers; keep configuration, SYNC binding and versions readable; bound every host-startable operation; and host-test every state × operation pair, not the happy path. §14.3 also notes that MCI is the Module-to-host control path, unrelated to the Managed Unit API of §14.1. The interface itself is defined by AES 0.7.0 (`AES-MCI-001` to `AES-MCI-005`).

## 0.3.0 - 2026-09-11

- Module Synchronization Interface (SYNC) firmware rules (§14.2): capture the SYNC IN edge with a hardware timestamp (input capture, edge interrupt with free-running counter, DMA or programmable I/O — never polling) and convert it to the Module's sample clock where one exists; keep the ISR minimal and decide in the owning task; model arming as an explicit state machine in which every unaccepted event is a logged ignored event with a reason, never an implicit restart, stop or queue; treat the SYNC IN action, SYNC OUT source, delay and post-completion mode as validated, versioned, readable runtime configuration; realize a configured delay on a hardware timer from the captured edge; generate SYNC OUT from the bound internal event through a hardware-timed output with characterized pipeline latency compensated, one source per output by default; never emit or interpret pulse patterns; log received, transmitted and ignored events with timestamp, sample index, state, run identifier, reason and local counters; host-test every state × event pair and measure latency and jitter on hardware. §14.1 clarifies that its hardware synchronization signal is Unit-to-host within one Module and unrelated to SYNC. The interface itself and its behavioral rules are defined by AES 0.6.0 (`AES-SYNC-001` to `AES-SYNC-004`, `docs/interfaces/sync.md`).

## 0.2.0 - 2026-07-14

- Managed Unit API rules (§14.1): a Managed Unit's public API must expose capabilities/operations/status/errors at a high level (no register-level internals in the host contract); the API must be versioned with defined framing, identifiers, status/error codes, timeouts and integrity checking; unknown commands and unsupported versions must fail safely; firmware identity and API version must be readable; the Unit must implement a disabled→starting→ready→fault lifecycle with `UIF_READY` gating valid transactions; and the host contract must not rely on software-latency timing where a hardware sync signal exists.

## 0.1.0 - 2026-07-13

First release.

- Design philosophy and a maturity-scaling model: safety rules always; reproducible builds, update integrity, watchdog and production diagnostics bind Released firmware; architecture, project layout, host tests and CI are the model firmware converges on as it matures.
- Firmware architecture: layered model, module responsibilities, active objects, policy/mechanism separation, initialization and lifecycle.
- Project structure, coding style, API design and error handling guidance.
- State machines, interrupt design, RTOS guidelines (for firmware that uses an RTOS), memory management (placement guidance for dynamic allocation) and concurrency rules.
- Logging and diagnostics, configuration management, communication interfaces and power management guidance.
- Firmware update, security and testing requirements scaled to maturity and risk.
- Documentation requirements aligned with the AURIORA Documentation Standard.
- A compact code review checklist (every change / concurrency and resources / toward Release); self-review explicitly valid.
- Requirement language aligned with AES (MUST/SHOULD/MAY; a skipped SHOULD needs no documented exception).
- Platform-independent policy: no references to specific languages, compilers, SDKs or vendors.
